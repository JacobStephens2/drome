# The sync round-trip tail is one store transaction

A signed-in phone applies one sync response as a single store transaction: check the reset epoch, ack the push, adopt or merge the config, then store the pulled events and assign the cursor. Either all of that commits or none of it does. The phone still owns the network hop, token refresh, and on-screen status. Both phones decide whether to run another round with one predicate: the outcome was stale, or the round applied and the push batch was full or the server set `more`. Adopting the account's challenge does not by itself schedule another round, because the winner and its events land in the same step.

Editing Android to copy iOS's old call order would have left the tail as three commits sequenced by the phone. A second process that shares the database can reset between those commits, and the next client would have to sequence them again. A transport port inside the store was the other alternative, and it loses: the hop is async, and token refresh and sign-out live on the phone. The cost of the transaction is that a test can no longer apply half a tail. That is the point. A half tail is no longer something a caller can do.
